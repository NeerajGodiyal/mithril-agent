# Mithril Agent

Mithril Agent is a programmatic automation layer for a Mithril Solana full node.
Its default direction is walletless and explorerless: read and index on-chain
program state, decode pinned interfaces, and simulate program calls without a
signing key. State-changing actions are a separate optional profile that reuses
the bounded policy, signer, submitter, recovery, Telegram, MCP, and Prometheus
work already built for the trading pilot.

The current end-to-end **execution** pilot is Devnet only. It proves bounded trading,
safety, recovery, and UX; broader workflows and Mainnet funded execution are disabled.

## Capability profiles

- **Observe and index (default):** no wallet application, signing key, or
  explorer. Mithril and a separate custom indexer supply the data.
- **Build and simulate:** no signing key; the pinned-interface builder handles
  Solana IDL 0.1.0 and bounded Codama 1.x codecs for local Mithril simulation.
- **Execute (optional):** a policy-approved action uses the existing isolated
  signer and submitter. Solana still requires a fee payer and any instruction
  authorities to sign, even when no browser wallet is part of the UX.
Today, read-only MCP, rooted events, restart-safe indexing, canonical Program
Metadata interface pinning, unsigned construction, simulation, and deterministic
Solana-IDL/Codama decoding cover the first two profiles.
One private workspace records the program and local paths without a wallet. Its
stdio MCP and the separate index MCP open no listener. See [`ROADMAP.md`](ROADMAP.md).

## What the optional trading capability has demonstrated

The Devnet pilot can:

- guide an operator through one saved strategy rather than separate service
  configurations;
- sell SOL for devUSDC, buy SOL back, and sweep excess SOL to a proven payout
  wallet;
- wait for sell-at-or-above and buy-at-or-below price conditions;
- limit time, action count, daily spending, fees, slippage, and the balance that
  must remain in the agent account;
- simulate and submit through the local Mithril node only;
- compare transaction fees, confirmations, transaction bytes, and balance
  effects through two independent read providers;
- keep the risk authority and signer behind separate socket-activated service
  identities, with the submitter, quote adapter, Telegram bot, and status
  bridge in separate processes;
- stop all configured legs together and restart in stopped mode;
- preserve hash-chained journals and bounded status for recovery and review;
- expose readable Telegram alerts, read-only MCP status, and Prometheus
  metrics; and
- watch Mainnet prices in shadow mode without any wallet-signing path.

The demonstrated live route is intentionally narrow: one fixed Devnet
SOL/devUSDC Orca route. Devnet proves mechanics and fail-closed behavior, not
profitability or readiness for arbitrary assets.

## Default architecture

```text
Mithril rooted replay -> RPC/MCP + rooted feed -> custom index -> operator
pinned interface -> deterministic builder -> simulation -> optional execution
```

```text
operator or agent framework
          |

          v

          |
          v
price, node, route, fee, and account checks
          |
          v

                                                    |
                                                    v
                                           sealed transaction
          |                                      |
          |                                      v
          +---------------------------> separate submitter process
                                                 |
                                                 v
                                      Mithril simulation + send
                                                 |
                                                 v
                                 independent confirmation evidence
                                                 |
                                                 v
                               journals + Telegram + MCP + metrics
```

The language model is not the security boundary. Codex, Claude, Hermes,
OpenClaw, or another MCP-capable client may explain status or suggest an
intent, but deterministic policy, signer limits, and an expiring operator grant
decide whether an action is allowed. The supplied Telegram and MCP interfaces
cannot approve, sign, or submit a transaction.

## Strategy model

A complete strategy has three possible legs on one dedicated account:

1. **Sell:** exchange a fixed amount of SOL for devUSDC when the configured
   sell condition is satisfied.
2. **Buy:** spend a fixed amount of devUSDC to buy SOL when the configured buy
   condition is satisfied.
3. **Sweep:** send only the SOL above a protected balance floor to the proven
   operator wallet on its configured schedule.

On a fresh account, the first sell creates the canonical devUSDC token account
and produces the funds needed by the buy leg. Setup therefore writes sell and
sweep first. After that first sell, `setup strategy --resume` adds the buy leg.
This is a one-time bootstrap, not a recurring manual step.

The important controls are independent:

- `trades_per_day` determines the signer's daily spending cap;
- `strategy enable --max-trades N` limits actions during one expiring grant;
- the per-action amount and maximum fee limit each transaction;
- price conditions constrain when a leg may run and the executable rate it may
  accept;
- `keep_sol` protects rent, fees, and funds required by armed legs; and
- `strategy stop` removes execution authority from every configured leg.

`--max-trades` is per trading leg. A value of `1` permits at most one sell and
one buy when both legs are configured; it does not permit an unbounded loop.
Market-price legs need `--allow-any-price`; `strategy dca-plan` only calculates an unauthorized fixed-input schedule. See `OPERATIONS.md` for the full boundary.

## Optional execution signing model

Observe/index and build/simulate do not load a signing key and do not require a
wallet application. The model below applies only after an operator enables a
state-changing capability.

The agent uses a dedicated, limited-balance account. It does not import or
operate the user's main wallet. The operator's Phantom, Solflare, or Solana CLI
wallet is used only as the sweep destination and signs a short proof showing
that the destination is controlled by the operator.

The browser-wallet path opens a temporary page through a localhost SSH tunnel.
The wallet signs in its own browser extension; the server never receives the
wallet key. The agent's Devnet signing key remains in a private file readable
only by the restricted signer service.

The runner cannot open the signing key, risk-authority key, or the signer's
durable daily ledger. It connects to separate per-leg Unix sockets; systemd
starts one confined risk-authority or signer instance for each request, loads
that instance's policy and key as private service credentials, and the instance
exits after replying. The signer re-decodes the exact message, checks its own
policy and daily ledger, then seals the signed transaction for the submitter.
The current Devnet runner never receives a raw signed byte slice, but it does
receive the exact signature and already holds the message, so it could
reconstruct that one policy-approved Devnet transaction. Treat the Devnet
submitter split as operational isolation, not as an adversarial boundary from a
compromised runner. The disconnected Mainnet package path fixes that boundary:
its runner-visible response withholds the transaction signature inside the
submitter-encrypted envelope. A separately identified submitter can recover it,
validate it, and check durable stop/grant state immediately before any future
submission.

Production execution can use a separately administered self-hosted signer or an
explicit transaction-only custody adapter. Both paths require distinct risk,
signing, attestation, and submission identities; both are qualification-only in
the current repository. `make test-free-custody` exercises the local boundary
without a provider account, RPC, funds, or broadcast, and `proposal
turnkey-check` verifies an explicitly configured Turnkey mapping without
signing. The separate-machine transport uses a forced OpenSSH command and pinned
host and policy identities. `mithril-agent proposal turnkey-check` verifies the
managed mapping. Mainnet services and live submission remain
disabled. See [OPERATIONS.md](OPERATIONS.md) for the exact policy, retry,
reconciliation, canary, and transport boundaries.

## RPC and evidence model

A live Devnet setup uses four protected RPC roles:

1. the operator's loopback Mithril RPC for verified state, simulation, and
   submission;
2. one HTTPS quote/read endpoint used only by the isolated quote sidecar;
3. a primary HTTPS evidence RPC; and
4. a secondary HTTPS evidence RPC controlled by a different provider.

Mithril is the only simulation and submission path. There is no external send
fallback. The two external evidence providers independently confirm what was
sent and what finalized, so the same node is not treated as the sole witness to
its own result.

Mithril's processed `getAccountInfo` context also carries a nonstandard `bankhash`. Canonical external PMP discovery
requires both reads to match on slot and bank hash, and preserves that hash so sibling banks cannot be spliced together.

Endpoints and credentials stay in root-owned service environment files. They
are not copied into strategy files, command-line arguments, journals, metrics,
MCP responses, or Telegram messages.

A Mithril node still catching up correctly blocks new actions. The node must be
near the cluster tip and must have replayed far enough to observe the agent
account. This is a safety requirement of this application, not a Solana
protocol rule.

## Telegram, MCP, and AI clients

Telegram is the phone-facing operations view. It reports strategy state, price
conditions, completed actions, and failures in readable language. Its supplied
commands are read-only; Telegram is not a wallet and does not carry signing
authority.

MCP exposes bounded node and agent status to compatible clients. An assistant
can inspect health, explain why a leg is waiting, summarize the last action,
and help an operator follow the documented recovery path. It must not receive
configuration contents, RPC URLs, credentials, wallet material, raw
transactions, or unrestricted service control.

Agent frameworks are interchangeable clients, not part of the signer. A user
can connect the MCP client they prefer without changing the policy or custody
boundary.

## Safe first look: no installation and no trading

On a development machine:

```sh
git clone https://github.com/NeerajGodiyal/mithril-agent.git
cd mithril-agent
make explain
make walkthrough
make test-free-rehearsal
```

`make explain` and `make walkthrough` never sign or install; `make test-free-rehearsal` checks the complete policy, custody, and submitter boundary with temporary, unfunded test identities entirely offline. `make test-account-free` adds current keyless market and Jupiter reads.
No operator wallet or custody-provider or messaging account is required. The strict public archive drill is separate: `make test-free-evidence`.
A local Devnet account and self-hosted production signer are supported; managed custody and Telegram are opt-in while local status, MCP, Prometheus, and journals remain available.

Those three commands do not need the Node.js quote adapter. Before installing or using the source on a live host, verify every prerequisite and build it:

```sh
make prereqs-trading
make verify-source
make test
make build
make adapter
```

`make build` produces all seven Go binaries. Keep them together; copying only
the main executable creates an incomplete runtime that setup refuses.

24.x line for the current Orca quote adapter.

Do not improvise the privileged commands from this summary. Follow

## Everyday operator commands

After the supervised installation:

```sh
sudo -u mithril-agent env HOME=/var/lib/mithril-agent \
  /usr/local/bin/mithril-agent doctor
sudo -u mithril-agent env HOME=/var/lib/mithril-agent \
  /usr/local/bin/mithril-agent strategy show
sudo -u mithril-agent env HOME=/var/lib/mithril-agent \
  /usr/local/bin/mithril-agent service install \
  --output /var/lib/mithril-agent/.mithril-agent/mithril-agent-run.service
sudo -u mithril-agent env HOME=/var/lib/mithril-agent \
  /usr/local/bin/mithril-agent strategy enable \
  --duration 12h --max-trades 1 --reason 'bounded demonstration'
sudo -u mithril-agent env HOME=/var/lib/mithril-agent \
  /usr/local/bin/mithril-agent strategy stop --reason 'operator stop'
```

`doctor` and `strategy show` are acceptance evidence; a zero service exit by
itself is not. Generated service files start in stopped mode and must not grant
trading authority during installation or restart.

Use [DEMO.md](DEMO.md) for either a no-trade review or an explicitly bounded
Devnet demonstration. Use [OPERATIONS.md](OPERATIONS.md) when a check fails or
when installing monitoring, rotating a provider, recovering a journal, or

## Current limits and Mainnet path

The repository does **not** currently provide:

- autonomous Mainnet strategy execution or submission;
- Solana v1 transaction decoding or signing; the existing legacy and v0 paths
  remain deliberately bounded;
- arbitrary tokens, arbitrary venues, perpetual futures, or leverage;
- approval or trade initiation through Telegram or an LLM;
- a proven profitable strategy;
- production custody defaults;
- a Mainnet-qualified submitter/custody authority. The bounded Devnet service
  isolates runtime calls, operator control, and recovery, but no KMS, HSM, MPC,
  or real-capital canary has been qualified; or
- permission to treat one RPC, including Mithril, as independent evidence for itself; or
- a reviewed immutable route-guard deployment. The v7 Mainnet profile refuses
  direct Jupiter messages and requires the exact guard program, ProgramData,
  deployment slot, code length, and code SHA-256. This repository ships no
  default deployment and Mainnet remains disabled.

Mainnet shadow mode holds no wallet signing key and is the current place to evaluate rules using
real prices. Its policy fingerprint binds the quote provider, pool, and token
pair alongside hypothetical decisions and fills, but has no dependency on signer or submitter code. Its continuous runner supports a single direction
or an alternating sell-then-buy-back round trip, with each return leg bounded
by what the preceding leg actually received. The offline replay command remains
available for deliberately modelled what-if analysis. Devnet remains the place
to prove the execution, policy, recovery, and UX mechanics.

Because the Mainnet route settles in USDC, shadow accounting does not silently
assume that USDC equals one dollar. Every observable Mainnet tick also requires
fresh, agreeing USDC/USD confidence intervals from Pyth's sponsored on-chain
feed through the configured RPC and Kraken's public timestamped order-book snapshot.
The generated policy pins a $0.99-$1.01 band; stale, disagreeing, or depegged
evidence makes the tick unobservable and prevents a hypothetical decision.
Reports bind their exact period end, include expected observations, and replay
each quote. `shadow review --days N` verifies consecutive complete Mainnet days
at 95% coverage without approving the strategy. Devnet makes no P&L claim.

The local `proposal check` command is the first read-only Mainnet execution boundary. It accepts
only the two current Jupiter V2 route shapes for an operator-approved Exact-In route between
native SOL and one classic SPL token, in either direction. For SOL input it independently verifies
the wallet's existing canonical output token account and rejects runtime creation. For token input
it verifies the canonical funded input account, keeps token spend separate from native fee caps,
and requires native output to return to the protected wallet. It also pins Jupiter's deployment,
verifies lookup tables and fees with independent evidence, and simulates the exact final message
through Mithril. Its successful result is deliberately `checked_not_authorized`: no wallet or
submitter consumes that result. A successful quote or simulation alone is never signing authorization.
The command binds two distinct provider trust domains and their credential-free
origins into the result and rejects an origin change during the full retained-message
evidence pass. The unsigned `proposal prepare` command can consume protected
authority policy, repeat that pass, and produce the exact unsigned, ungranted
signer request. Before a grant, offline `proposal review` independently decodes
that exact request under the signer policy and prints only bounded amounts,
mints, schedule, debit, and hashes; it neither validates authorization nor loads
a key. `proposal approval-create` then verifies a separate operator wallet's off-chain signature over that exact review and writes a detached approval; it
cannot sign or send a transaction. Provider qualification is bound to an operator-chosen old finalized v0 transaction;
both independent RPCs must recover the exact same transaction and effects, so
a recent-only endpoint cannot pass as an archive provider. The read-only `proposal
evidence-check` runs it without a wallet, provider account, or signing key. An optional private candidate artifact carries
the exact message and canonical lookup-table evidence across that process
boundary without carrying provider selection, a signature, or a key. The
unsigned request binds the protected provider identities into its request hash,
and the submitter requires an exact match with its own protected configuration. The offline, account-free `proposal policy-create` command writes matching authority, signer, and submitter policies from the checked route, provider pins, and public identities; it creates no key and grants no authority. Before use, `proposal bundle-check` verifies the candidate and all three policies, while identity-only authority and submitter checks prove their installed keys match that bundle; every result remains explicitly unauthorized.
The submitter command can independently validate a sealed version-0 response
and create the exact durable pre-send recovery record without opening an RPC or
broadcasting. The policy-authority and signer packages cover the
intervening risk-grant and provider-neutral transaction-only custody
boundaries. A pinned Turnkey transaction-signing adapter covers the provider
API contract and exact-retry behavior and is available only as an explicit
signer CLI/socket backend; generated services do not select it and the live
submit command remains Devnet-only. The keyless `mithril-agent proposal canary-check` command verifies
the exact detached approval, binds the matching multi-day shadow evidence, then repeats the complete
Mithril and two-provider check. Keyless `--recover` resolves only matching finalized effects. Keyless `--retire-mainnet` works
only while fully stopped and archives a proposal that never reached send-started, preserving private
audit evidence and refusing started or previously retired actions. None can submit.

Production also requires explicit owners for the venue and asset allowlist,
strategy and loss limits, signer/custody boundary, independent evidence
providers, external deadman, off-host append-only audit copy, crash-recovery mode, and tiny Mainnet
canary procedure, including atomic protection from a route-program upgrade. The recommended first canary, if self-hosted custody is
chosen, uses a new limited-balance wallet and a separate exact-policy signer;
it never imports an operator's primary wallet and never gives Telegram, MCP, or
an LLM signing authority.

## Verification

The complete local check is:

```sh
make test
```

It runs formatting, `go vet`, full tests, the race detector, isolation checks,
and refuses private runtime artifacts in the source checkout. The shorter loop is:

```sh
make test-short
```

Every push and pull request verifies the manifest, runs Go and Rust checks, builds all seven release binaries, and runs `govulncheck`. External
actions are pinned to immutable releases. `make build-route-guard
ROUTE_GUARD_OUT=/absolute/private/path` separately requires Agave CLI 4.2+ and
neither deploys nor activates the guard.

Live tests are separate because they require explicit public inputs and a
running environment. The Devnet demonstration must remain bounded and must be
followed by journal, status, Telegram, and independent confirmation checks.
